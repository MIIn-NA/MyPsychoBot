# Отчёт об интеграции решателя

Класс, уверенность и совет для ответа Telegram и записи в SQLite берутся из одного
`SolverResult`. Подмена прогноза по `negative_words` отсутствует.

Первая предварительная оценка предлагает уточнить описание текстом или выбрать
тему кнопкой. Исходное описание сохраняется только в состоянии диалога и
объединяется с уточнением для повторного `solve()`. При повторной низкой оценке
показывается предварительный результат и предлагается новый анализ. Отмена
очищает ожидающее уточнение и исходный текст.

В SQLite записываются только оценки с уверенностью не ниже порога. Ошибка записи
журналируется; пользователь получает сформированный ответ без подтверждения
сохранения. Пустой ввод и превышение лимита сопровождаются конкретной подсказкой.
Сбой предсказания или недоступность RuBERT приводят к сообщению о недоступности
анализа. MockModel включается только явно: `BOT_DEMO_MODE=1`.

## Расхождение с запиской

На рис. 2.4 (диаграмма последовательности) в записке предусмотрено сохранение исходного
сообщения. Текущая таблица `results` в `bot/storage.py` хранит только результаты
анализа: идентификаторы, группу, дату, класс, уверенность и совет. Поля исходного
сообщения нет. В этой реализации исходное описание хранится временно в состоянии
диалога, но не записывается в SQLite. Для согласования диаграммы с реализацией
необходимо отдельно пересмотреть записку либо спроектировать хранение сообщений.
Исходные сообщения в рамках этой задачи в SQLite не сохраняются; обучение
модели не изменялось.

## Проверки

`python3 -m unittest discover -s tests -v` — 80 тестов проходят.
Проверены уточнение текстом и кнопкой, отмена, повторная низкая оценка, сохранение
только итоговых оценок, граница порога, пустой и длинный ввод, недоступная модель,
демонстрационный режим и сбой SQLite. Проверки выполнялись с заглушками без
сетевого подключения Telegram и загрузки весов RuBERT. Хранилище дополнительно
проверено на настоящей SQLite во временных каталогах.

## Единое хранилище SQLite

Реализация сверена с §§2.2–2.5 `../Соловей_Записка.pdf`: накопление результатов
отделено от решателя, групповая выборка использует группу и период, отсутствие
данных не подменяется оценками, добавлен индекс по группе и дате.

`Storage()` выбирает `db/results.db` относительно `Path(__file__).resolve()`.
`init_table()` создаёт родительский каталог, проверяет обязательные колонки через
`PRAGMA table_info(results)` и добавляет индекс `idx_results_group_date`.
Повторная инициализация не удаляет записи. Ошибка инициализации останавливает
запуск до Telegram polling. Личная статистика больше не открывает отдельное
соединение из обработчика: все запросы идут через общий экземпляр `Storage`.
Существующий `StatisticsService` использует этот же экземпляр для групповых
выборок; новые команды и роли психолога в рамках этой правки не добавлялись.

Корневая `psycho_bot.db` оставлена нетронутой и не мигрируется: в старой схеме
нет `group_name`, поэтому восстановить группу автоматически нельзя.
Совместимая база в `db/` сохраняется. Расхождение записки с фактическим хранением
исходных сообщений, описанное выше, остаётся: сохраняются результаты анализа.

Хранилище и интеграция проверены на настоящей SQLite во временных каталогах:
путь независимо от каталога запуска, создание каталогов, сохранение через
обработчик, личная и групповая статистика, границы периода и порядок записей,
повторная инициализация, индекс, отказ для несовместимой схемы без изменения
данных, ошибки чтения и записи, откат при сбое commit и запуск до polling.
Валидация отдельно проверена до открытия базы, включая bool, неверные даты,
NaN и бесконечности; уверенность сохраняется без округления.

## Чтение статистики и ограничения

`Storage.get_user_class_counts(user_id)` одним параметризованным запросом
возвращает количества классов текущего пользователя. `/stats` использует этот
метод и `sum(counts.values())`; отдельного пути к базе и SQL в обработчике нет.
Для пустой статистики и сбоя чтения сохранены разные ответы. Старый метод
`get_user_stats` делегирует новому для совместимости.

`get_results(group, start_date, end_date)` сохраняет ключи словарей, проверяет
реальные даты формата YYYY-MM-DD и порядок границ, включает обе даты и сортирует
по `analysis_date, id`. Пустая выборка — `[]`; ошибка чтения передаётся вызывающему
коду, а не маскируется отсутствием данных.

Хранилище возвращает записи, а `StatisticsService` считает количества и доли
состояний и формирует агрегированный текстовый отчёт и PNG-график дневных долей.
Проверка роли психолога и подключение группового отчёта к Telegram пока не
реализованы и относятся к вызывающему компоненту. В боте пока используется
`group=1`: все новые записи относятся к одной группе до подключения реальных
учебных групп. Это ограничение не позволяет считать текущие записи статистикой
разных учебных групп.

## Групповой отчёт с графиком

Сервис доработан по §§2.1–2.2, §2.5 и сценарию рис. 2.3: выбор группы и периода,
получение сохранённых результатов, расчёт агрегатов и формирование отчёта.
`get_summary()` сохраняет прежний текстовый интерфейс без загрузки Matplotlib.
`get_report()` возвращает `GroupReport(summary, chart_png, daily_aggregates)`.
За вызов выполняется ровно один `await storage.get_results(...)`; и текст,
и изображение используют одни рассчитанные агрегаты. Прямого SQL, другой базы
и классификатора в сервисе нет. Проверки группы (положительное целое, кроме bool)
и периода выполняются до чтения, контракт дат совпадает с Storage.

`aggregate_results()` отделён от отрисовки: считает все анализы, группирует
по календарным датам и сортирует дни. `DailyAggregate.counts` содержит количества
классов 0/1/2, `total` — число анализов за день, `percentages` — дневные доли.
Повторные анализы учитываются отдельно. Итоговые доли считаются от общего числа
анализов периода, а не усреднением дневных процентов.

PNG строится в памяти через Matplotlib Agg, без GUI и pyplot, в рабочем потоке;
одновременная отрисовка защищена блокировкой. На графике три ряда дневных долей;
пропущенные дни обозначаются разрывами без вымышленных наблюдений.
При пустой выборке возвращаются сообщение об отсутствии данных, `chart_png=None`
и пустые дневные агрегаты. Ошибки чтения и отрисовки передаются вызывающему коду
и не подменяются отсутствием данных. В отчёт не включаются советы, идентификаторы
студентов и исходные сообщения; график не устанавливает медицинские группы риска.

Проверены общий расчёт, доли и порядок дней, единственная выборка, отсутствие
отрисовки в текстовом методе и при пустых данных, валидация, передача ошибок,
интеграция с SQLite и корректность PNG для одного дня и периода с пропусками.
Telegram и проверка роли психолога остаются задачей вызывающего компонента.

Уточнён контракт расчётов: один проход по записям, доли за период — от общего
числа анализов, точки графика — от числа анализов конкретного дня. Проценты
до вывода текста не округляются. Названия показателей — «число анализов»
и «доля анализов»; отсутствие класса в день с наблюдениями даёт 0%, отсутствие
наблюдений даёт разрыв линии через NaN, а не нулевую оценку. При полностью
пустой выборке текст начинается с «За выбранный период данных нет» и содержит
группу и даты; PNG отсутствует. Неизвестный класс, отсутствующая или повреждённая
дата вызывают `StatisticsDataError`, ошибки SQLite проходят без подмены.
Отдельные тесты проверяют единственный проход, неравные дневные объёмы,
точность процентов, нулевые классы, разрывы и передачу ошибок данных обоими методами.

Для периода с единственным днём наблюдений добавлено пояснение: сравнивать
динамику пока не с чем. Классы в сводке идут в порядке «Норма», «Стресс»,
«Тревога». Шкала PNG ограничена 0–100% и подписана процентами; у серий разные
маркеры, легенда вынесена за область данных. Даты выбираются автоматическим
локатором с ограниченной плотностью; для однодневного запроса остаётся одна
подпись даты. PNG для одного дня и семилетнего периода проверены визуально.
Автотесты подтверждают отдельную фигуру для каждого отчёта, декодирование PNG
и отсутствие индивидуальных полей в отчёте и аргументах отрисовки. Изображение
возвращается готовыми байтами из BytesIO, временный файл для Telegram не нужен.

## Граница доступа в Telegram

В этой задаче подготовлены сервис и контракт подключения группового отчёта.
В проекте сейчас нет проверки роли психолога; групповой обработчик Telegram
не добавлен. Доступность `StatisticsService.get_report()` сама по себе не
означает, что сценарий психолога по рис. 2.3 подключён.

При будущем подключении порядок обязателен: Telegram-обработчик проверяет роль
психолога, затем вызывает `get_report()` или групповой `get_summary()`, после
чего сервис запрашивает `Storage.get_results()`. При отказе в доступе запрос
к сервису и хранилищу не выполняется. Проверка только перед отправкой уже
сформированного отчёта этому контракту не соответствует. Сервис не принимает
пользователя Telegram и не подменяет проверку его роли.

Личная команда `/stats` и кнопка «Моя статистика 📊» сохранены: обработчик
передаёт `message.from_user.id` в `get_user_class_counts()` и показывает только
собственные количества пользователя.

Отдельное ограничение: при сохранении результатов в боте пока задано `group=1`.
Все новые записи относятся к одной группе. До подключения реальных учебных
групп это не статистика распределения по фактическим группам студентов.
